# Tower Defense (JUEGO CAÑONES)

Browser tower-defense game: vanilla JS ES modules + Canvas 2D in `game/`, no build step. Tests: `cd game && node --test` (all must pass). The user speaks Spanish: talk to them in Spanish.

## The user's rules

- Commit locally as you go; `git push` and the Vercel deploy (project `torres-defensa`, https://torres-defensa.vercel.app, Vercel CLI from `game/`) only when the user says a round of changes is done. Ask before publishing. Never enter credentials: the user logs in to Vercel themselves.
- `node server.js` (port 8421 since the user's own commit 8e50bec; 8420 before) is a shared LAN game people may be playing: never restart it without asking. To test, use `PORT=8432 DATA_DIR=<temp dir> node server.js`, or the no-cache static server `python tools/serve_nocache.py game 8431`.
- Never ship Command & Conquer images (copyrighted). Don't rewrite git history.
- Don't spawn subagents unless the user asks.
- The game plays music: before testing in a browser set localStorage `td_settings` to `{"music":false,"effects":false}`, and close the tab afterwards.

## The 3D art: units, turrets, the RTS base and the maps

- The army (tank, buggy, motorcycle, rocket truck, soldier), the defence's three turrets and the RTS mode's base (its seven buildings, the wall block, the harvester, the MCV, the ore crystals) are 3D models built by Blender scripts in `tools/blender/` (`units.py`, `towers.py`, `rts.py`, on `kit.py`); nothing is modelled by hand. `blender -b --factory-startup -P tools/blender/build.py -- <out> <name> <preview|icon|glb|sprites>` renders one job, and `python tools/blender/pack_sprites.py <out> game/assets <name>...` puts the results in `game/assets/units3d/` (sprite sheets, pictures, icons) and `game/assets/models/` (GLB, for the RTS mode's 3D view).
- `game/js/unitSprites.js` holds each model's numbers (frame size, scale, where the turret and the muzzle are) and how a unit looks from frame to frame (hull easing, turret aiming, wheels, walk, recoil). They must match `SPECS` in the Blender scripts. It is looks only: the simulation doesn't know about it.
- Maps are built the same way, from the game's own data: `node tools/blender/maps/dump_level.mjs <N> <json>` writes a level's roads, wall, gates and build slots; `maps/level<N>_layout.py` (plain Python: numpy + PIL) lays the map out and paints its ground; `maps/level<N>_build.py` (Blender) models what stands on it and renders the map and its foreground (what the game draws over the units); `maps/pack_map.py` puts them in `game/assets/maps/`. Change a road in `levels.js` and the map has to be rendered again. Towers can stand on any build slot, so nothing solid goes on one: ruins' walls run on the lines half-way between slots, trees stand where four slots' squares meet.
- All four levels' maps are built this way: level 3 by its own `level3_layout.py` / `level3_build.py` (it is also the RTS mode's map: `pack_map.py <dir> game/assets 3 3d` ships its flat ground and its model for the 3D view too), levels 1, 2 and 4 by `level<N>_layout.py` on `paintkit.py` and the one `build_map.py` on `scenekit.py`. Levels 1 and 2 (1200 x 750) are rendered at twice their size. A building hides what is behind it, so none stands where its picture would cover a build slot or a road.
- Still on older pictures: the defence mode's wall blocks and support buildings.

## The duel minigame

- A fifth way to play, asked for on 2026-11-22: two small armies, bought, upgraded and placed by their players, fight by themselves in an arena, round after round, first to three. Design: `docs/2026-11-22-duelo-design.md` (the table at its top holds what the user decided). Four plans: (A) the core without a screen -- done (`docs/2026-11-22-duelo-nucleo-plan.md`); (B) the screen, the menu and the first arena -- done (`docs/2026-11-24-duelo-pantalla-plan.md`); (C) balance with simulated duels and the other four arenas -- done (`docs/2026-11-24-duelo-equilibrio-plan.md`); (D) the home network -- done (`docs/2026-11-24-duelo-red-plan.md`). Online duels are a later phase (the design's §13).
- The core is four DOM-free modules that touch no other mode: `js/duel.js` (state, actions, a deterministic fixed-step fight from a seed, `duelView` for what a side may see), `js/duelArenas.js` (zones and mirrored round obstacles), `js/duelProfile.js` (level, skill points, league, in the browser's storage) and `js/duelAI.js` (the computer's five grades, playing through the same actions from a view).
- On screen: `js/duelScreen.js` runs a duel against the computer (the state, the computer's turns, the pointer, the profile at the end), `js/duelDraw.js` paints it, `js/duelUI.js` says what its panels show (pure functions, tested) and builds them; `duel.css` styles the profile's screen and the result. While the game's mode is `"duel"`, `main.js`'s `loop()` and pointer handlers hand everything to it (`dueling()`), and the attack mode's shop and unit panel elements hold the duel's (`mountAttackPanels()` puts the attack's back). A duel is never saved. Against the computer it runs in the browser even on the home server's page, like the RTS mode (`localDuel`; the house's news are kept aside meanwhile, `heldSnapshot`).
- Between two players the home server holds the duel (`host.js`, kind `"duel"`; `versus.js`'s seats serve any two sides, here `left` and `right`): `newDuel` creates it and waits, paused, for the second player; `join`, `duelBuy` / `duelSell` / `duelMove` / `duelUpgrade` / `duelReady`, `pause`, `rematch`; each tab gets `duelView(state, its side)` (nobody's shopping, for a tab only watching). In the browser `duelScreen.js` then runs the duel from the server's news (`netDuel()`: `frame(dt, { remote: { state, net, ask, address } })`), drawing the units between the last two pieces of news and posting the player's actions. Test it with two tabs against `PORT=8432 DATA_DIR=<temp dir> node server.js`: two tabs of one browser are two players (the id is in `sessionStorage`) but share one profile (`localStorage`).
- An arena's picture is built like a map's: `node tools/blender/maps/dump_arena.mjs <N> <json>`, `python tools/blender/maps/duel1_layout.py <json> <dir>` (arena 1) or `duel_layout.py` (arenas 2 to 5: one script, a theme an arena, its props made of plain shapes and its own surfaces, which `build_map.py` builds from the layout's `solids` and `paints`), `blender ... build_map.py -- <dir> duel<N> render 96 2`, `python tools/blender/maps/pack_map.py <dir> game/assets duel<N>`, and `art: true` in `js/duelArenas.js`. What stands up must stand inside the arena's obstacle circles (the wall round the arena is outside both zones). Move an obstacle and its arena has to be rendered again.
- The units' numbers in `DUEL_UNITS`, the grades in `DUEL_GRADES` and the experience a level takes were tuned with simulated fights and careers (`node tools/duel/matrix.mjs game 100 200 350`, `node tools/duel/career.mjs game <head 1-5> <careers>`; what they showed is in the plan C document) and carry comments saying so; tests hold the outcome (tanks beat light units, rockets beat tanks, motorcycles and buggies beat rockets; each grade beats the one before). The «sensible player» of those careers is the computer's own grade-3 head: once people have played, set the grades again from how they did. The prices are the attack mode's (a test holds them together).

## The musical duel (a trial, not a design yet)

- Asked for on 2026-11-25 (the user's son): a duel whose fight is a rhythm game -- the league's song plays, arrows and numbers fall down the screen for both sides at once, and a mistake brings a volley of the rival's army. The user wants six songs, one a league, and a sixth league, Platino, above Oro. So far there is a trial of one league (Arena) against the computer, for the user to try before deciding: `docs/2026-11-25-duelo-musical-prueba.md` says what was asked, what the trial does and which rules were my own calls (to be confirmed or changed by the user, then written up as a design).
- `js/duelSongs.js` holds the songs as notes (no sound files) and the keys made from them (the tune's own notes: an arrow a pitch, a number on each bar's first note); `js/duelRhythm.js` the rules, on a duel's state with a `musical` part (`createMusicalDuel`, `pressKey`, `stepMusicalDuel`; the shop and the rounds stay `duel.js`'s); `js/duelMusic.js` plays a song with oscillators, following the fight's own clock (so it stops with a pause and can't drift from the keys); `js/duelRhythmDraw.js` draws the track of keys. `duelScreen.js` runs it (`start(arena, { musical })`, `key(code)`); the menu's «Duelo musical (prueba)» starts one. It leaves the profile alone and is local only.
- I can't hear the song: it was checked by rendering it to a buffer in the browser (`OfflineAudioContext`) and measuring each voice's level. How it sounds is for the user to say -- and of the written one he said «mega horrible» (2026-11-25): he wants real songs made with Suno instead, in the style of rhythm-battle games, and long presses, which are in (`releaseKey`; a key with `hold` seconds).
- Recorded songs: `python tools/duel/chart_from_audio.py <sound file> <league> --name "..."` (ffmpeg, numpy, scipy) finds a recording's tempo, beats and bars, writes its keys (numbers on the low strokes by their beat of the bar, arrows on the tune, long keys on held notes), copies it to `game/assets/music/duel<N>.mp3`, keeps what it found in `tools/duel/tracks/<N>.json` and writes `game/js/duelTracks.js` from all of those. A league with a track plays it (the fight then follows the music's clock, `duelMusic.js`'s `follow`; each round starts at the song's next `starts`); one without plays the written song. `python tools/duel/test_chart_from_audio.py` checks the tool on songs made with a known beat. No real song has gone through it yet: the user is to make one in Suno and say where the file is; listen to its report (the beat's contrast, how far it strayed) and expect to tune `write_keys`.
- The musical duel's tests put `TRACKS` aside (they stand on the written song), so a new recording can't break them; the pane used for testing is usually hidden, where frames come once a second and a browser lets no sound out without a real click: step the duel by hand (`stepMusicalDuel` on `window.__gameState()`) and send key events.

## How the work is done

- Each part of the roadmap gets a design doc (the spec, approved by the user) and implementation plans in `docs/`, executed task by task with TDD (a test that fails first). Decisions the spec doesn't settle are recorded as rulings, each with what it costs if wrong, and reported to the user at the end with the deferred minor issues.
- Roadmap the user approved, in order: (1) main menu + saved games -- done; (2) attack mode against a computer defence -- done (`docs/2026-10-09-modo-atacante-*`); (3) one against the other on the home network -- done (`docs/2026-10-09-uno-contra-otro-*`); (4) online rooms with a code -- hosting still undecided (a room server on the user's VPS, Supabase Realtime, or P2P/WebRTC).
- The defence game's balance must not change by accident. Changes to shared code (`enemy.js`, `simulate.js`) used by other modes are opt-in for those modes (see `stepEnemy`'s `turnFirst` option), and gameplay changes are checked with seeded headless bot games, old code against new.
- The attack mode was tuned with the headless bot `game/js/attackBot.js` (it is published with the game: the phones' automatic army, `autoArmy.js`, uses it too, and `js/deploy.test.js` fails if `.vercelignore` leaves out a module the browser loads); the tuned values carry comments saying so.
